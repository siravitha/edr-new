# ระบบบริหารครุภัณฑ์อัจฉริยะ โรงพยาบาลอุดรธานี

## จัดการผู้ใช้และตำแหน่ง — ส่วนต้นแบบ

เมนู “จัดการผู้ใช้งาน” มีหน้าต่างเพิ่ม/แก้ไข ชื่อ รหัสบุคลากร ตำแหน่ง หน่วยงาน บทบาท วันเริ่ม–สิ้นสุด และคำสั่งแต่งตั้ง/มอบอำนาจ เลือกมุมมอง “ผู้ดูแลระบบ · จำลอง” เพื่อทดลองบันทึก ข้อมูลเก็บร่วมกับทะเบียนจำลองใน IndexedDB ป้องกันรหัสซ้ำและการระงับ/ลดสิทธิ์ผู้ดูแลจำลองคนสุดท้าย

ตำแหน่งไม่ให้สิทธิ์อนุมัติอัตโนมัติ ผู้ใช้ใหม่อยู่สถานะรอยืนยันตัวตน ข้อมูลคำสั่งเป็นร่างรอตรวจ ไม่มีการส่งอีเมล สร้างรหัสผ่าน ออก session หรือเชื่อม Provider ID และไม่เปลี่ยนสิทธิ์เข้าเว็บไซต์ส่วนตัวของบริการ Sites ห้ามกรอกข้อมูลบุคลากรจริงลงต้นแบบนี้ การเลือกบทบาทเป็นเครื่องมือสาธิต ไม่ใช่ระบบป้องกันสิทธิ์ production

## ระยะที่ 2 — วงจรพัสดุภาครัฐครบ 15 ขั้นตอน

เพิ่มหน้าวงจร 15 ขั้นตอนตามลำดับที่ยืนยัน ประเภทงาน 7 แบบและแหล่งเงิน 3 แบบ ตัวจำลองผูกพัน/ทยอยจ่ายโดยไม่หักงบซ้ำ การตรวจรุ่นและเลขอ้างอิงจ่ายซ้ำ และค่าเสื่อมตามนโยบายที่ส่งเข้าฟังก์ชัน พร้อมแยกการจำหน่ายเป็นการตรวจจริง อนุมัติ และดำเนินการ

อ่านรายงานออกแบบฉบับเต็มใน `docs/PHASE2-AGENTROOM.md` แบบฐานข้อมูลใหม่อยู่ใน `prisma/phase2.prisma` และ SQL ตัวอย่าง `prisma/phase2-initial.sql`/`prisma/phase2-guards.sql` แยกจาก migration ของ API เดิม ยังไม่ได้นำไปใช้กับฐานข้อมูลใด

ผลตรวจล่าสุด: ชุดทดสอบ 38 กรณีผ่าน, Prisma validate ระยะที่ 2 ผ่าน และ TypeScript ของบริการผ่าน ยังไม่ได้ทดสอบ MySQL จริงหรือเชื่อมระบบโรงพยาบาล

**นโยบายออฟไลน์ยังไม่กำหนด:** API `/api/sync` ที่คำสั่งผ่าน auth/role/schema แล้วจะปฏิเสธ 503 `OFFLINE_POLICY_UNAPPROVED` ก่อนเข้าฐานข้อมูล ไม่มีตัวแปรแวดล้อมสำหรับข้าม การจำลองคิวเดิมบนหน้าเว็บยังทดลองได้เฉพาะในเครื่อง เอกสารรายละเอียด API ระยะที่ 1 ด้านล่างเป็นแกนโค้ดที่ยังไม่เปิดใช้งานจริง

หน้าตัวอย่าง 15 ขั้นและตัวจำลองงบใช้หน่วยความจำและรีเซ็ตเมื่อออกจากหน้า เป็นคนละส่วนกับทะเบียน/คิวเดิมที่เก็บ IndexedDB ตัวกรองประเภทงานและแหล่งเงินยังเป็นบริบทสาธิต ไม่ได้เปลี่ยนกฎบัญชีหรือสร้างวิธีจัดหาอัตโนมัติ

## เริ่มทดลอง

เปิดลิงก์ต้นแบบที่ส่งมอบในแชต กด “วิธีทดลอง” มุมขวาบน เลือกบทบาทจำลอง แล้วเริ่มทำรายการ ข้อมูลทั้งหมดเป็นข้อมูลสังเคราะห์และเก็บแยกตามเบราว์เซอร์/ที่อยู่เว็บ ไม่เชื่อมข้อมูลผู้ป่วยหรือฐานข้อมูลโรงพยาบาล

## ทำได้ในรุ่นนี้

- หน้าจอภาษาไทยสำหรับเดสก์ท็อป แท็บเล็ต และมือถือ ด้วย Next.js 16 / React 19 / Tailwind 4 พร้อมองค์ประกอบรูปแบบ Shadcn และ Recharts
- ภาพรวม KPI สี่ตัว กราฟแนวโน้มตัวอย่าง และ Heatmap ที่เปิดรายการตามหน่วยงานได้
- ทะเบียน 40 รายการ ค้นหา กรอง แบ่งหน้า ดูรายละเอียด และส่งออก CSV ตามตัวกรอง
- อ่านรหัสจากเครื่องสแกนที่ทำงานเสมือนแป้นพิมพ์ หรือกรอกรหัสตัวอย่าง ยังไม่เปิดกล้องอ่าน QR
- นำเข้า CSV มีแม่แบบ ตรวจหัวตาราง จำนวนแถว ราคา หน่วยงาน และเลขทะเบียนซ้ำ พร้อมแสดงข้อผิดพลาดก่อนยืนยัน รายการใหม่อยู่สถานะรอตรวจรับรอง
- คิวออฟไลน์เก็บใน IndexedDB พร้อม Service Worker แคชหน้าเว็บหลังเข้าใช้งานครั้งแรก ปิดงานอนุมัติในโหมดออฟไลน์
- ซิงก์จำลองแบบตรวจรุ่น ป้องกันคำสั่งซ้ำ และเก็บคำสั่งขัดแย้งทั้งสองฝั่ง
- จำลองสองแท็บเล็ตที่ส่งสถานะจากรุ่นเดียวกัน และเวิร์กโฟลว์ส่งคืนคำขอเบิกจ่ายหลังปิด PO โดยคงรุ่นเดิม
- โครงบริการ Node.js/Fastify/TypeScript พร้อม Prisma 6/MySQL และ SQL migration สำหรับพัฒนาระบบจริงแยกจากเว็บสาธิต
- API ซิงก์ตรวจ internal JWT แบบ RS256 และขอบเขตโรงพยาบาล/วอร์ด ล็อกแถว ทำ receipt/audit/conflict ในธุรกรรมเดียวกัน

## ทดลองสถานการณ์หลัก

1. เลือก “เจ้าหน้าที่คลัง” → คิวซิงก์และข้อขัดแย้ง → จำลองออฟไลน์
2. กดสแกนครุภัณฑ์ → ลองรหัสตัวอย่าง → ยืนยันเก็บคำสั่ง แล้วโหลดหน้าใหม่ คำสั่งยังอยู่ เลือกบทบาทเดิมเพื่อซิงก์
3. กลับออนไลน์ → ซิงก์คิวของฉัน → ดูสถานะและประวัติ
4. กดจำลองแท็บเล็ตสองเครื่องชนกัน → ดูสถานะปัจจุบันและสถานะที่คำสั่งเก่าเสนอ ระบบไม่เลือกตามนาฬิกาแท็บเล็ต
5. เลือก “การเงิน” → ตรวจคำขอ PAY-2569-0142 → ใส่เหตุผลและส่งคืน → เปลี่ยนเป็น “พัสดุ” → สร้างรุ่นใหม่ สถานะ PO ยังคง CLOSED
6. หน้าเชื่อมต่อระบบมีปุ่มรีเซ็ตเฉพาะข้อมูลสาธิต เมื่อต้องการเริ่มใหม่

ใช้แท็บเดียวต่อที่อยู่เว็บสำหรับแก้ข้อมูลต้นแบบ มี Web Locks ป้องกันแท็บที่สองเขียนทับ snapshot เดิม แท็บที่เปิดเพิ่มอ่านได้อย่างเดียว และควรโหลดใหม่หลังปิดแท็บแรก หากเบราว์เซอร์ไม่มี Web Locks จะปิดการเขียนเพื่อความปลอดภัย

## เปิดในเครื่องสำหรับทีมพัฒนา

แนะนำ Node.js 22 LTS ขึ้นไป ติดตั้งที่โฟลเดอร์โครงการ:

```powershell
npm ci
npm run build
npm start
```

เปิด `http://127.0.0.1:4173` หรือใช้ `npm run dev` เพื่อแก้ไขหน้าเว็บ Service Worker เตรียมจากผล build เท่านั้น โหมดพัฒนาไม่รับรองแคชออฟไลน์

หากเครื่องจำกัดสิทธิ์เขียน npm cache ให้ตั้ง `npm_config_cache` เป็นโฟลเดอร์ภายในพื้นที่ทำงานของทีมก่อนติดตั้ง ไม่ต้องใช้สิทธิ์ผู้ดูแลระบบ

## ตรวจบริการและทดสอบ

```powershell
npm --prefix backend ci
npm --prefix backend run prisma:generate
npm --prefix backend run build
npm test
```

Prisma generate/validate ต้องมีตัวแปร `DATABASE_URL` รูปแบบ MySQL ที่ถูกต้อง ไม่ต้องเชื่อมฐานข้อมูลระหว่างสร้าง client ส่วนชุดทดสอบ API ใช้กุญแจ RSA ชั่วคราวในหน่วยความจำและฐานข้อมูลจำลองที่ไม่ถูกเรียกใช้ ไม่มีการเข้าถึงระบบโรงพยาบาล

รายละเอียดบริการและการตั้งค่าอยู่ใน `backend/README.md` และ `backend/.env.example` ต้องตั้ง issuer, audience และ public key จึงเปิดบริการได้ ไม่มีบัญชีข้ามการยืนยันตัวตน

## ฐานข้อมูล

`prisma/schema.prisma` และ `prisma/migrations/` มีโครงตารางและ trigger ป้องกันแก้/ลบประวัติ ก่อนใช้จริงต้องตรวจ migration บน MySQL ทดสอบและใช้บัญชีจัดการโครงสร้างที่แยกจาก runtime ไม่ได้รัน migration กับฐานข้อมูลใดในงานนี้

```powershell
npx prisma migrate deploy --schema prisma/schema.prisma
```

ใช้คำสั่งข้างต้นเฉพาะเมื่อทีมกำหนดฐานข้อมูลเป้าหมายและตรวจ migration แล้วเท่านั้น `prisma/audit-guards.sql` เป็นตัวอย่างสำหรับติดตั้งด้วย MySQL client แทน migration ของ trigger; เลือกวิธีเดียวเพื่อไม่สร้างชื่อ trigger ซ้ำ

## ขอบเขตที่ยังต้องพัฒนา

เว็บสาธิตเป็น static export และ **ยังไม่ได้เรียก API หลังบ้าน** ตัวเลือกบทบาทและการติ๊กหลักฐานเป็นการจำลอง ไม่ใช่ authentication, 2FA, ลายเซ็น หรือการตรวจหลักฐานจริง รูปแบบรหัส/คำสั่งใน demo มี adapter ต่างจาก API จริงซึ่งใช้ UUID และต้องมีเหตุผลประกอบ

ก่อนใช้งานจริงต้องทำ Provider ID callback และการตรวจระดับ 2FA, ตรวจสิทธิ์/การเพิกถอนจากทะเบียนปัจจุบัน, ลงทะเบียนอุปกรณ์, ตัวเชื่อม HOSxP ที่ได้รับอนุญาตแบบอ่านอย่างเดียว, ขั้นตอนผู้ตรวจตัดสินข้อขัดแย้ง, การอนุมัติตามวงเงินและคำสั่งแต่งตั้ง, รายการบัญชีสมดุล/การกลับรายการ และการกระทบยอด e-GP/GFMIS ตามระบบของโรงพยาบาล

ยังไม่มี OCR, Excel .xlsx, RFID, Aruba ingestion จริง, การรับอัปโหลด/ตรวจลายเซ็นหมึกจริง, การเข้ารหัสข้อมูลออฟไลน์ระดับอุปกรณ์, outbox/WORM/hash checkpoint นอกฐานข้อมูล หรือการรับรองความสอดคล้อง PDPA/สตง. การป้องกันแก้ไขของ audit ในเครื่องเป็นเพียงสาธิต ผู้ใช้ล้างข้อมูลเบราว์เซอร์ได้

การทดสอบธุรกรรมพร้อมกัน, unique receipt, rollback และ trigger บน **MySQL จริงยังไม่ได้ดำเนินการ** ต้องทำกับฐานทดสอบก่อนเปิดใช้ API ไม่ควรนำข้อมูลโรงพยาบาลจริงเข้าสู่พื้นที่ทดลองนี้

## โครงสร้าง

- `app/` — หน้าจอและรูปแบบภาษาไทย
- `components/ui/` — องค์ประกอบปุ่มและการ์ด
- `lib/` — ข้อมูลตัวอย่าง ตรรกะโดเมน การเก็บออฟไลน์ และ CSV
- `public/` / `scripts/` — การสร้างแคชออฟไลน์และเซิร์ฟเวอร์แสดงผล
- `backend/` — บริการ API ที่ต้องตั้งค่าก่อนเปิด
- `prisma/` — สคีมาและ migration
- `tests/` — ทดสอบตรรกะ นำเข้าไฟล์ และการปฏิเสธคำขอ API
