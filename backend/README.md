# บริการหลังบ้านสำหรับต้นแบบครุภัณฑ์ โรงพยาบาลอุดรธานี

## สถานะระยะที่ 2

นโยบายออฟไลน์ของโรงพยาบาลยังไม่กำหนด จึงระงับคำสั่ง `/api/sync` ที่ผ่านการตรวจ auth/role/schema ด้วย HTTP503 `OFFLINE_POLICY_UNAPPROVED` ก่อนเข้าฐานข้อมูล ไม่มี environment flag ให้ข้าม การคืน APPLIED/CONFLICT ในรายละเอียดด้านล่างเป็นแกนกระบวนการที่ยังไม่เปิดใช้จนกว่าจะมีนโยบายและบริการตรวจสิทธิ์ปัจจุบันจริง

`src/policy.ts` เป็นตัวช่วยตรวจป้ายและตัวอย่างประเมินนโยบาย/สิทธิ์ออฟไลน์ ข้อมูล trusted ต้องสร้างจากเซิร์ฟเวอร์เท่านั้น ห้ามส่ง `req.body` ไปเป็นตัวตนหรือนโยบายโดยตรง ตัวช่วยนี้อนุญาตเพียงร่างข้อสังเกตตาม allowlist ที่ผ่านนโยบาย ไม่อนุมัติจ่ายเงินหรือจำหน่าย

แบบข้อมูลใหม่ `../prisma/phase2.prisma` เป็นแบบแยกที่ผ่านการตรวจรูปแบบและสร้าง SQL แล้ว ยังไม่ได้เปลี่ยน Prisma Client ที่บริการนี้ใช้หรือ apply กับฐานใด อ่าน `../docs/PHASE2-AGENTROOM.md` สำหรับขอบเขตและข้อจำกัดล่าสุด

ส่วนนี้เป็นโครงร่าง Node.js/TypeScript + Fastify + Prisma 6/MySQL สำหรับ Pacific Plus IT ยังไม่ใช่ระบบที่ผ่านการรับรองใช้งานจริง และยังไม่เชื่อม Provider ID, HOSxP, e-GP หรือระบบบัญชี การมี Provider ID ในโทเคนไม่ได้ยืนยันว่าได้ทำ 2FA หรือลงนามเอกสารแล้ว

## เตรียมระบบ

ใช้ Node.js 22 ขึ้นไป ติดตั้งแพ็กเกจใน `backend/` แล้วกำหนดตัวแปรจาก `.env.example` ผ่านระบบจัดการความลับหรือ `node --env-file=.env` โดยไม่ส่งไฟล์ความลับเข้า Git ตั้งค่า `DATABASE_URL` ให้ Prisma CLI เห็นด้วย สร้าง client ด้วย `npm run prisma:generate` และ migration ด้วยบัญชีจัดการโครงสร้างแยกจากบัญชี runtime จากนั้นใช้ `npm run build` และ `node --env-file=.env dist/server.js` ระบบจะหยุดทันทีหาก issuer, audience หรือกุญแจ JWT ขาดหาย ไม่มีบัญชีข้ามการยืนยันตัวตน

JWT เป็นโทเคน RS256 ที่ผู้ออกภายในโรงพยาบาลลงนามหลังเชื่อมตัวตนจริง ต้องมี `sub`, `iss`, `aud`, `iat`, `exp`, `hospitalId`, `deviceId`, `roles`, `wards`, `token_use: "access"` และอาจมี `providerRef` อายุสูงสุด 15 นาที สัญญาโทเคนภายในนี้กำหนดชนิด access ชัดเจนเพื่อไม่รับ ID token; ห้ามส่งโทเคน Provider ID ตรงมายัง API นี้ ตัวอย่าง role ที่เขียนได้คือ `WARD` และ `WAREHOUSE`; `ADMIN` ไม่ได้ข้ามขอบเขตวอร์ด ผู้ใช้ส่ง hospital/device/สิทธิ์ผ่าน body ไม่ได้ ตัวตนผูกกับ issuer ที่ตั้งค่าไว้

## คำสั่งซิงก์

`POST /api/sync` พร้อม Bearer token และ JSON `{ "mutationId": "UUID", "assetId": "UUID", "baseVersion": 0, "status": "IN_USE", "reason": "รับใช้งานในหอผู้ป่วย" }` ยอมรับสถานะ AVAILABLE, IN_USE, REPAIR, QUARANTINED ตามกติกาเปลี่ยนสถานะ จำกัดเนื้อหา 4 KiB และปฏิเสธฟิลด์ส่วนเกิน `WARD` ขอได้เฉพาะ IN_USE หรือ REPAIR; `WAREHOUSE` ขอได้ตามตารางสถานะ ระบบห้าม REPAIR → AVAILABLE ผ่านแท็บเล็ต การรับรองซ่อมเสร็จและการจำหน่ายต้องใช้เส้นทางอนุมัติที่ยังไม่ได้พัฒนา ส่วน QUARANTINED → REPAIR ใช้ส่งซ่อมได้แต่ไม่ใช่การรับรองกลับใช้งาน

ระบบล็อกแถวตาม hospital และ asset ก่อนตรวจ version จากนั้นบันทึกการเปลี่ยนแปลง audit และ receipt ภายในธุรกรรมเดียวกัน คำสั่ง mutation เดิมที่มีเนื้อหาและผู้ใช้เดิมให้ผลและสถานะ HTTP เดิม (APPLIED = 200, CONFLICT = 409) หาก version ไม่ตรงจะบันทึก conflict และตั้ง needsReview โดยไม่เขียนสถานะทับ เครื่องแรกที่มาถึงไม่ได้ถือว่าเป็นข้อเท็จจริงโดยอัตโนมัติ หัวหน้าคลังต้องตรวจหลักฐานแล้วออกคำสั่งแก้ไขใหม่ เส้นทางแก้ข้อขัดแย้งยังไม่ได้พัฒนา

## หลักฐานและข้อจำกัดที่ต้องทำก่อนใช้งานจริง

- รัน `../prisma/audit-guards.sql` หลัง migration ด้วยบัญชีผู้ดูแล ใช้บัญชี runtime ที่อ่าน/เพิ่ม audit และ receipt ได้เท่านั้น สิทธิ์กว้างอาจทำให้ trigger ถูกลบได้ ฐานข้อมูลนี้ยังไม่มี WORM หรือ hash checkpoint ภายนอก จึงไม่อ้างว่าต้านผู้ดูแลฐานข้อมูลได้
- ตรวจสิทธิ์จากฐานข้อมูล/ระบบนโยบายปัจจุบันและทะเบียนอุปกรณ์ทุกครั้งก่อนใช้งานจริง ขณะนี้เชื่อ claims ที่ลงนามและอาจเก่าได้ถึง 15 นาที ยังไม่มีเพิกถอน session/device ทันที
- เปิด TLS, จำกัดอัตราคำขอและจำนวน connection ที่ reverse proxy และเพิ่มการจัดการปิดระบบอย่างเป็นระเบียบก่อน production ปัจจุบันไม่เชื่อ forwarded IP และไม่เปิด CORS ข้าม origin
- ต้องเพิ่มกระบวนการอนุมัติ การตรวจรับครบจำนวน การแยกหน้าที่ ผู้มีอำนาจ วงเงิน งวดบัญชี และการกลับรายการ Schema ไม่ได้บังคับทุกกฎของระเบียบพัสดุ
- ไม่เก็บข้อมูลผู้ป่วยในระบบนี้ กำหนดฐานกฎหมาย สิทธิ์เข้าถึง และอายุเก็บตัวตน/IP ร่วมกับ DPO และฝ่ายกฎหมาย สตง. ไม่ได้ถูกรับรองโดยการมี audit table เพียงอย่างเดียว
- ยังไม่มี migration ที่สร้างแล้ว ไม่มี seed และไม่มีการทดสอบกับฐานข้อมูลจริงในชุดส่งมอบนี้ ต้องทดสอบแข่งซิงก์/ส่งซ้ำ การหลุดเชื่อมต่อ การแยก hospital/ward และสิทธิ์ audit โดยใช้ MySQL ก่อนติดตั้ง
